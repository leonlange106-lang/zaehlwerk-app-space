## 2. Der erste Schritt (mit CLI-Zugriff)

Das Ziel ist nicht „noch ein Tag", sondern **einmal zusehen**. Auf dem Server:

```sh
cd <repo>
git fetch --tags && git checkout v3.12.0-beta.9

# Der Kern: die Migration braucht die Datenbank allein.
docker stop zaehlwerk-main-portal
docker compose -f docker-compose.prod.yml --profile tools run --rm db-migrate
docker compose -f docker-compose.prod.yml up -d
```

Erwartet: `Applying migration 20260728160000_ablesung_soft_delete`, danach
`All migrations have been successfully applied.` Anschließend `migrate status`
gegenprüfen und die App aufrufen.

Schlägt das fehl, **liegt der Befund vor der nächsten Codeänderung** — nicht
danach. Das ist der Fehler dieser Sitzung, in einem Satz.

### Das Live-Protokoll friert dabei ein — das ist kein Absturz

Beobachtet am 2026-07-28 um 22:03: Das Update-Protokoll blieb bei Build-Schritt
`#14` stehen und sah aus, als hinge der Build. Er hing nicht.

Die Migration hält `zaehlwerk-main-portal` an — und damit stirbt der
SSE-Stream (`api/system/update/stream`), der das Protokoll live nachliefert.
Die Seite bleibt bei der letzten empfangenen Zeile stehen. **Ein Refresh nach
dem Neustart zeigt den wahren Stand**, in diesem Fall die erwartete Meldung
„Datenbank migriert … bitte das Update erneut starten".

Das ist offen: Die Oberfläche sollte das ankündigen, statt es den Nutzer
erraten zu lassen — sonst liest es jeder als sechsten Fehlschlag. Kandidat für
`UI-02` (Ladezustände) oder einen eigenen kleinen Punkt.

## 3. Was schiefging, damit es niemand erneut herleitet

Alles unten ist **gemessen**, nicht geschlossen. Die Belege stehen in
`packages/database/scripts/test-migrations.mjs` und `scripts/test-deploy-swap.mjs`.

### Die Ursache

`main-portal` ist gleichzeitig **die Anwendung**, **der Halter der Datenbank**
und **der Prozess, der das Update ausführt**. Daraus folgt alles andere.

Prismas Schema-Engine verträgt neben sich **keine offene Transaktion** — auch
keine lesende, auch im WAL-Modus:

| Zustand der laufenden Anwendung | `prisma migrate deploy` |
|---|---|
| nur verbunden, keine Transaktion | läuft |
| offene **Lese**transaktion | **gesperrt** |
| offene Schreibtransaktion | **gesperrt** |

Eine laufende App hat ständig welche (das automatische Backup liest mit
`VACUUM INTO` über die ganze Kopie). Also muss die Migration die App anhalten —
und hält damit den Prozess an, der das Update ausführt.

### Sackgassen (nicht noch einmal)

| Versuch | PR | Warum es nicht reichte |
|---|---|---|
| Baseline nur einmal stempeln | #122 | Richtig, aber nicht die Ursache |
| WAL sicherstellen, Backup verschieben, Budget 1 → 3 min | #123 | Die Instanz war längst auf WAL |
| Anhalten in `update.sh`/`deploy-swap.sh` | #124, #125 | `update.sh` kommt aus dem **Image** — greift erst beim übernächsten Update |
| `- .:/repo` an `db-migrate` | #125 | Bind-Mount-Quellen löst der **Host**-Daemon auf → leeres Verzeichnis über dem Code |

Weitere Sackgassen, jeweils ausprobiert und verworfen: `busy_timeout` an den
Schema-Engine reichen (`socket_timeout`, `connection_limit` — beides wirkungslos);
den `journal_mode`-Wechsel aussitzen (SQLite meldet sofort `SQLITE_BUSY`, ohne
den Busy-Handler zu fragen).

### Wo es jetzt steht (`3ac646d`)

`deploy-migrations.sh` hält den Container **über seinen Namen** an — aber nur,
wenn `migrate status` wirklich offene Migrationen meldet. Sonst bliebe der
Updater bei *jedem* Update auf der Strecke.

Praktische Folge: **Der erste Update-Lauf endet mit einer Meldung, die wie ein
Fehler aussieht** („Datenbank migriert … bitte das Update erneut starten"). Der
zweite Lauf findet nichts mehr anzuwenden, hält nichts an und geht durch.

## 4. Prioritäten für morgen

### 1. `PLT-01` — eigenständige Dienste (höchste Priorität, Wunsch des Nutzers)

Der Punkt ist **nicht das Portal**, sondern die Auflösung der Dreifachrolle
oben. Eigene Container je App heißt: eigene Datenbank, ein Update betrifft nur
sich selbst, wer migriert hält niemanden auf, den er braucht.

Details in `docs/backlog.md`. Reihenfolge dort: Spike (Auth über
Dienstgrenzen, Discovery-Quelle, Datenhoheit) → Admin-/User-Ansicht → Portal.
**Die Admin-/User-Ansicht hängt an nichts davon** und ist schon am heutigen
Monolithen wertvoll — wenn nur ein Teil kommt, dann dieser.

Die geteilte **Benutzerverwaltung** ist die eine Stelle, die dabei sorgfältig
gelöst werden muss.

## 6. Zwei Arbeitsgewohnheiten, die diese Sitzung teuer gelernt hat

**Messen, bevor man schließt.** Vier der sechs Fehlschläge kamen aus plausiblen
Schlüssen, die falsch waren („WAL löst das", „Wiederholen reicht"). Die
entscheidende Tabelle oben entstand in zehn Minuten mit drei Prozessen und
einer SQLite-Datei — nach dem vierten Fehlschlag statt vor dem ersten.

**Ein Test, der auch ohne den Fix besteht, beweist nichts.** Zweimal passiert:
ein Halter, der die Sperre gar nicht hielt, und ein Compose-Aufruf von außen,
der die Pfadfalle des echten Ablaufs nicht traf. Zu jedem Regressionstest hier
gehört die Gegenprobe — Fix entfernen, Test muss fallen.
